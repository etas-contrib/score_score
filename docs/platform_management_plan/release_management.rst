PF Release Management Plan
==========================

This document implements the applicable parts of :need:`wp__platform_mgmt`.


Purpose
-------

The Release Management Plan defines how releases of the S-CORE software
platform and its modules are planned, prepared, verified, approved, identified,
and made available.


Objectives and Scope
--------------------

The objective of this plan is to define:

* the scope and content of a release;
* the supported release types;
* how releases are planned, prepared, verified, and approved;
* how platform and module releases are coordinated; and
* how releases are identified, versioned, and baselined.

Approach
--------

Release Scope
~~~~~~~~~~~~~

A release represents a defined, version-controlled state of a repository.
Consequently, S-CORE distinguishes between a platform release and separate
releases of individual modules.

A release includes the repository content identified by the corresponding
release tag, together with the applicable verification evidence and generated
documentation artifacts associated with that repository state.

Verification evidence includes the applicable verification reports and relevant
inputs, such as test execution logs.

Generated documentation artifacts include, for example, the HTML documentation
generated by the CI build for publication on the S-CORE website.

Binaries generated by the CI build are not released as qualified S-CORE work
products. Users are expected to build binaries from the released source within
the context of their applicable target system and build environment.

The released source, build configuration, and identified dependencies provide
the basis for reproducing the corresponding build.

Release Types
~~~~~~~~~~~~~

Release types are related to the release versioning scheme defined in the
`Identification`_ section.

S-CORE distinguishes between two main release types: **experimental** and
**official**. These correspond to the applicable feature flags defined in
:need:`doc__project_mgt_plan`.

* **Experimental releases** may contain incomplete development artifacts with
  respect to the work products required for the applicable safety package.
  They are created during development primarily to support synchronization,
  integration, and verification across module repositories.

  Experimental releases shall be clearly identifiable as such and shall not be
  considered equivalent to an official release.

* **Official releases** require the applicable development and verification
  processes to be completed and the required work products to be available in
  their required state.

  Each official release shall be documented by a release note according to
  :need:`gd_temp__rel_plat_rel_note` or :need:`gd_temp__rel_mod_rel_note`, as
  applicable.

  Official releases shall additionally comply with the applicable Eclipse
  Foundation release requirements.

Release Planning and Execution
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Release planning and execution follow the process defined in
:need:`wf__rel_mod_rel_note`.

Release planning is part of the overall project planning and uses the same
planning infrastructure. A planned release is represented by an ISSUE associated
with the corresponding GitHub Milestone.

The release ISSUE tracks the activities required to prepare and complete the
release. The corresponding release note is created or updated through a Pull
Request and forms part of the release documentation.

Before an official release, the features included in the release enter a
stabilization period. During this period, no new planned functional development
is accepted for the release.

Changes during stabilization are restricted to activities required to complete
the release, including:

* bug fixes;
* verification and test activities;
* resolution of findings identified during verification; and
* quality improvements required to meet the applicable release criteria.

The stabilization period is planned by the Technical Leads as part of milestone
planning. No fixed duration is prescribed. For the initial releases, a
stabilization period of approximately four weeks is recommended. The duration
may be reduced as the maturity and stability of the platform and modules
increase.

Module and platform releases shall be coordinated according to the applicable
release process.

The platform release shall identify the versions of the module releases included
in the platform baseline.

Where modules expose compatibility-relevant interfaces to one another, their
release versions shall follow the applicable compatibility and versioning rules.

Release execution shall follow the steps defined in
:ref:`module_release_manual`.

Release Verification and Approval
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Before a module or platform release is finalized, its release readiness shall be
verified and approved by the :need:`rl__quality_manager` and the
:need:`rl__project_lead` according to :need:`wf__vy_ap_modrelease` and
:need:`wf__vy_ap_pltrelease`, as applicable.

The release-readiness review confirms, as applicable, that:

* the process conformance check defined by :need:`wp__qms_report` has been
  successfully completed;
* :need:`wp__qms_plan` is up to date with respect to the Quantitative Quality
  Goals defined in :need:`doc__platform_quality_plan`;
* the required Work Product Reviews according to :need:`wf__exe_wp_review` have
  been successfully completed;
* the applicable review and verification results are documented in
  :need:`wp__verification_platform_ver_report` or
  :need:`wp__verification_module_ver_report`, as applicable;
* release-relevant work products have reached the lifecycle state required by
  the applicable Work Product Quality Goals defined in
  :need:`doc__platform_quality_plan`; and
* the release baseline and corresponding release note consistently identify the
  content of the release.

The release shall only be finalized after the applicable release-readiness
criteria have been fulfilled and the required approvals have been recorded.

Identification
~~~~~~~~~~~~~~

S-CORE release versions follow Semantic Versioning using the
``MAJOR.MINOR.PATCH`` format.


1. Semantic Versioning Format
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

Release versions use the following format::

   MAJOR.MINOR.PATCH


2. Version Components
^^^^^^^^^^^^^^^^^^^^^

* **MAJOR** is incremented for incompatible changes to the public interface.
* **MINOR** is incremented for backward-compatible functionality additions.
* **PATCH** is incremented for backward-compatible corrections.


3. Rules for Incrementing Versions
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

**Major Version (MAJOR)**

The MAJOR version is incremented when changes introduce incompatibilities with
the previous public interface.

Examples include:

* removal or incompatible modification of public APIs; and
* architectural or interface changes that require incompatible modifications
  in consuming modules.

**Minor Version (MINOR)**

The MINOR version is incremented when functionality is added in a
backward-compatible manner.

Examples include:

* addition of new backward-compatible APIs or capabilities; and
* extensions to existing functionality that preserve backward compatibility.

**Patch Version (PATCH)**

The PATCH version is incremented for backward-compatible corrections.

Examples include:

* correction of defects in existing functionality; and
* compatible non-functional changes that do not introduce new functionality or
  incompatible interface changes.


4. Pre-Release Versions
^^^^^^^^^^^^^^^^^^^^^^^

Pre-release identifiers may be used to identify versions that precede the
corresponding final release.

The format is::

   MAJOR.MINOR.PATCH-<pre-release-tag>

Examples include ``1.0.0-alpha`` and ``1.0.0-beta``.

Pre-release versions shall be clearly distinguishable from the corresponding
final release.


5. Release Tags
^^^^^^^^^^^^^^^

Each release is identified by a Git tag corresponding to its release version.

For final releases, the tag format is::

   vMAJOR.MINOR.PATCH

For example, version ``1.3.0`` is identified by tag ``v1.3.0``.

For pre-release versions, the pre-release identifier shall also be included in
the tag, for example::

   v1.0.0-alpha
