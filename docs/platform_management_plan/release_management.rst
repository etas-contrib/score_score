PF Release Management Plan
==========================

This document implements parts of :need:`wp__platform_mgmt`.

Purpose
-------

The Release Management Plan defines how releases of the S-CORE software platform and its modules are planned, executed, verified, approved, and identified.

Objectives and Scope
--------------------

The objective of this plan is to define:

* the scope and contents of a release,
* the supported release types,
* how releases are planned and executed, and
* how releases are identified and versioned.

Approach
--------

Release Scope
~~~~~~~~~~~~~

A release comprises all version-controlled files of a repository. Consequently, S-CORE distinguishes between a platform release and separate releases of the individual modules.

A release also includes the verification reports and their relevant inputs, such as test execution logs, as well as documentation artifacts generated by the CI build from the release-tagged repository content. This includes, for example, the generated HTML documentation for the S-CORE website.

Binaries generated by the CI build are not part of the release. They are not qualified S-CORE work products and are expected to be rebuilt by users within the context of their target system. Since the Bazel-based build is reproducible, the binaries can be recreated from the released source at any time.

Release Types
~~~~~~~~~~~~~

Release types are closely related to the release versioning scheme described in the `Identification`_ section below.

S-CORE distinguishes between two main release types: **experimental** and **official**. These correspond to the feature flags defined in :need:`doc__project_mgt_plan`.

* **Experimental releases** may contain incomplete development artifacts with respect to the work products required for the safety package. They are created during development, primarily to synchronize development and integration across module repositories.

* **Official releases** require the applicable development and verification processes to be completed and the required work products to be available. Each official release is documented by a release note according to :need:`gd_temp__rel_plat_rel_note` or :need:`gd_temp__rel_mod_rel_note`.

  Official releases shall additionally consider the `Eclipse Project Handbook - Releases <https://www.eclipse.org/projects/handbook/#release-releases>`_.

Release Planning and Execution
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Release planning and execution follow the process defined in :need:`wf__rel_mod_rel_note`.

Release planning is part of the overall project planning and uses the same planning infrastructure. A release is generally represented by an issue associated with a milestone in the `GitHub Milestone Planning <https://github.com/orgs/eclipse-score/projects/13>`_. The release issue is completed by merging a pull request that creates or updates the corresponding release note.

Before each release, the features included in the release enter a stabilization period. During this period, no new functional changes are accepted. Changes are restricted to bug fixes, additional verification and test activities, and quality improvements.

The stabilization period is planned by the Technical Leads as part of milestone planning. No fixed duration is prescribed. For the initial releases, a stabilization period of approximately four weeks is recommended. This period may be reduced as the maturity and stability of the modules increase.

Module and platform releases shall be coordinated as defined by the release process. Because a major-version increment indicates an incompatible API change, modules included in a platform release are expected to use the same major version.

Release execution shall follow the steps defined in :ref:`module_release_manual`.

Release Verification and Approval
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Before a module or platform release is finalized, it shall be verified and approved by the :need:`rl__quality_manager` and the :need:`rl__project_lead` according to :need:`wf__vy_ap_modrelease` and :need:`wf__vy_ap_pltrelease`.

The approval confirms that:

* the process conformance check defined by :need:`wp__qms_report` has been successfully performed,
* :need:`wp__qms_plan` is up to date, in accordance with the Quantitative Quality Goals defined in :need:`doc__platform_quality_plan`,
* the required Work Product Reviews according to :need:`wf__exe_wp_review` have been successfully completed,
* the applicable review results are documented in :need:`wp__verification_platform_ver_report` or :need:`wp__verification_module_ver_report`, and
* release-relevant work products are not left in draft or template state, in accordance with the Work Product Quality Goals defined in :need:`doc__platform_quality_plan`.

Identification
~~~~~~~~~~~~~~

1. **Semantic Versioning Format**

   Release versions use the ``MAJOR.MINOR.PATCH`` format.

2. **Version Components**

   * **MAJOR** is incremented for incompatible API changes.
   * **MINOR** is incremented for backward-compatible functionality additions.
   * **PATCH** is incremented for backward-compatible bug fixes.

3. **Rules for Incrementing Versions**

   **Major Version (MAJOR)**

   The MAJOR version is incremented when changes introduce incompatibilities with the previous public API.

   Examples include:

   * removal or incompatible modification of public APIs, and
   * architectural changes that require modifications in dependent modules.

   **Minor Version (MINOR)**

   The MINOR version is incremented when functionality is added in a backward-compatible manner.

   Examples include:

   * addition of new APIs or modules, and
   * extensions to existing functionality that preserve backward compatibility.

   **Patch Version (PATCH)**

   The PATCH version is incremented for backward-compatible corrections and non-functional improvements.

   Examples include:

   * correction of defects in existing functionality, and
   * minor improvements that do not introduce new functionality or incompatible changes.

4. **Pre-Release Versions**

   Pre-release identifiers are used for releases that are not yet considered ready for an official release.

   The format is::

      MAJOR.MINOR.PATCH-<pre-release-tag>

   Examples include ``1.0.0-alpha`` and ``1.0.0-beta``.

5. **Release Tags**

   Each release is identified by a repository tag corresponding to its version.

   The tag format is::

      vMAJOR.MINOR.PATCH

   For example: ``v1.3.0``.
